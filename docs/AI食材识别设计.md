# 从操作步骤识别食材 — 功能设计

> 这份文档记录的是单个功能的交互约定。跨页面通用的设计语境(用户、色板、字号、通用原则)在仓库根目录的 `.impeccable.md`。

## 场景

家庭菜谱管理员在手机上整理家庭已有菜谱。很多菜谱已经写好了操作步骤,但食材列表是空的或不全的。目标是**减少逐行补录食材**,而不是改写菜谱步骤。

## 输入与输出

- 输入:菜谱当前已记录的操作步骤,**只读**。
- 输出:对食材草稿的一组建议,分为两组呈现:
  - **新增** — 步骤里出现、食材表里没有的
  - **可能多余** — 食材表里有、步骤里没出现的

菜谱食材现在只保存名称和 `usedUp`（用完 / 有剩），不再填写用量。AI 确认新增的食材默认标记为用完，用户可以在食材列表中切换；已有食材的标记保持不变。

每一条建议都要显示它的依据(来自第几步 / 原文片段)和确定程度;低置信度的条目不能和高置信度的长得一样。

## 交互约定

1. AI 只提出建议,用户逐条或整体确认后才改变食材草稿。
2. 操作步骤是只读输入,任何识别失败都不能破坏原有记录。
3. 暂存建议与最终保存分离:接受建议只更新草稿,只有用户点击"保存菜谱"才提交。
4. 保留现有手动编辑路径。AI 不可用、超时或返回空结果时,用户仍能照常填写并保存菜谱——入口降级,而不是页面不可用。

## 语气

给出有依据的建议,不把猜测伪装成事实。文案示例:

- 好:「第 3 步提到"两勺生抽",食材里没有,要加上吗?」
- 差:「已为您智能识别并自动补全 5 项食材」
## 差异语义

AI 只负责从步骤中提取有证据的候选食材、数量、单位和来源步骤。新增、修改、可能多余等差异由服务端使用确定性规则计算,不交给模型直接决定。

- 使用服务端现有的 `normalizeName()` 做基础名称匹配。
- 完全匹配的食材保留。
- 步骤中出现、当前草稿没有的食材进入「新增」。
- 当前草稿存在、步骤中没有明确提及的食材进入「可能多余」,默认不选中,不能直接删除。
- 为兼容已有 AI 提取契约，服务端仍可返回用量、单位、「修改」和「待补用量」信息；编辑页不展示或应用这些用量建议，也不要求补填用量。
- 番茄/西红柿等模糊别名首期不自动合并,需要用户确认。

「可能多余」只表示“步骤中未提及”,不表示食材一定错误。油、盐、水等基础食材尤其不能因为缺少步骤证据就自动删除。

## 表单约束

- 操作步骤仍是 `string[]` 的只读输入,AI 请求期间也不能用返回结果覆盖步骤。
- AI 建议只存在于编辑页草稿中,点击「应用选中建议」才修改食材行,点击「保存菜谱」才调用现有创建/更新接口。
- AI 没有识别出可靠数字时，附带信息使用 `quantity: null` 和 `quantityText`，不能编造数字。
- 步骤明确写出“2 勺”“300 毫升”“3 个”时，AI 可以提取数值和单位作为附带信息，不写入菜谱食材。
- 食材保存使用 `{ name, usedUp }`；没有用量的 AI 新增食材也可以直接保存。
- 用户修改步骤、食材名称或“用完 / 有剩”标记后，正在等待或已展示的 AI 建议失效，必须重新整理。

## 云端动作契约

复用 `recipe` 云函数,新增动作 `recipe.extractIngredients`,不新增数据库集合,不在识别阶段写入菜谱。

请求 payload:

```json
{
  "steps": ["五花肉切块", "锅中倒油,加入生抽和冰糖"],
  "existingIngredients": [
    { "name": "五花肉", "quantity": null, "unit": "" },
    { "name": "盐", "quantity": null, "unit": "" }
  ]
}
```

服务端把 `steps` 发送给腾讯混元,`existingIngredients` 只用于服务端差异计算。成功结果至少包含:

```json
{
  "detected": [
    {
      "name": "生抽",
      "quantity": 2,
      "unit": "勺",
      "quantityText": "两勺",
      "evidenceStepIndexes": [1],
      "evidenceQuotes": ["加入生抽"],
      "confidence": "high"
    }
  ],
  "diff": {
    "add": [],
    "update": [],
    "removeCandidates": [],
    "needsQuantity": []
  },
  "warnings": []
}
```

约束:

- 需要已登录且属于有效家庭成员的身份上下文。
- 请求沿用统一 `requestId`,用于错误追踪和客户端重试;识别结果不做幂等持久化。
- 校验步骤数量、单步长度和总输入长度,超限返回 `VALIDATION_ERROR`。
- 混元调用只发生在云函数,密钥不能进入小程序包、Git 或普通日志。
- 模型输出必须经过 JSON 解析、字段白名单、数量/单位/来源步骤校验;非法输出按安全错误返回。
- 不记录完整步骤、完整食材列表或完整模型请求到 `operation_logs`。
- 需要设置超时、重复点击保护和用户级调用限制;失败时保留原草稿并允许手动继续。

`recipe` 云函数通过 OpenAI 兼容的 Chat Completions 接口调用 AI 服务,只需要三个服务端环境变量:

- `AI_API_KEY`: API Key,必填,不能进入仓库。
- `AI_BASE_URL`: 兼容接口基础地址,必填,必须使用 HTTPS,例如腾讯混元的 `https://api.hunyuan.cloud.tencent.com/v1`。
- `AI_MODEL`: 模型名,必填,由所选服务商提供,例如 `hunyuan-turbos-latest`。

请求超时固定为 20 秒,单个云函数实例中每个用户每分钟最多请求 5 次。这些运行策略不需要额外环境变量。API Key 只进入云函数环境变量,不进入小程序包、Git 或普通日志。

完整请求地址为 `${AI_BASE_URL}/chat/completions`;认证方式为 `Authorization: Bearer ${AI_API_KEY}`。服务商必须兼容 `messages`、`tools` 和 `tool_choice` 参数,并返回 OpenAI 风格的 `tool_calls`。正式生产环境仍需在服务商侧配置账号额度和跨实例配额。

## 实现前置修复

编辑已有菜谱的云端更新链路已修复：`recipe.update` 的 `normalizePatch()` 会规范化并写入 `ingredients`，其中每项包含名称和布尔类型的 `usedUp`。

回归测试需要确认新建和编辑都能保存:

- 新建菜谱保存完整食材。
- 编辑已有菜谱修改、新增和删除食材后,云端返回和下一次详情查询均反映新列表。
- 未知字段仍然被拒绝。

## 页面状态和文案

至少覆盖:

- 无步骤:「先写下至少一个操作步骤,再让 AI 帮你整理食材」。
- 加载中:按钮禁用并显示「正在从步骤里找食材…」,不允许重复请求。
- 有结果:按新增、可能多余分组,每行展示来源步骤和确定程度。
- 空结果:「没有找到明确的食材,原有清单没有改变」,保留手动编辑。
- 超时/服务失败:「暂时没整理出来,原有食材没有改变,可以继续手动填写」,提供重试。
- 请求期间用户修改了步骤或食材:丢弃过期结果,提示「内容已经变过了,请重新整理」。

整体操作应命名为「应用选中建议」,不能使用暗示无条件覆盖的「自动补全」或「全部替换」。删除建议默认不选中。

## 验收与测试

使用真实家庭菜谱样本覆盖:

- 明确数量和单位;
- 只有食材名称、没有数量;
- “适量”“少许”“一把”等模糊用量;
- 步骤中省略油、盐、水;
- 当前食材多余、缺少、重复和别名;
- 混元返回空结果、非法 JSON、超时和网络错误;
- 新建与编辑两条保存链路。

自动化测试不直接调用线上模型,使用 fake provider 验证 handler、输出校验和差异计算。小程序测试加载提交的编译 `.js` 页面文件;每个修改的 `.ts` 必须同步更新对应 `.js`。
