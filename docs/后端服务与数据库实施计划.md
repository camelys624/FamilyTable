> 文档版本：V1.0
>
> 更新日期：2026-07-22
>
> 状态：待实施，可直接拆分开发任务
>
> 默认方案：微信云开发 CloudBase（云函数、文档数据库、日志）

## 1. 文档目标与实施边界

本文档是家庭菜单微信小程序 MVP 的后端专项实施基线，目标是把当前仅依赖 `miniprogram/services/store.ts` 和微信本地缓存的演示版本，渐进迁移为可供多成员共同使用、按家庭隔离、可测试和可发布的云端服务。

本文档负责定义：

- CloudBase 的工程边界、三套环境和认证方式；
- 数据集合、字段、索引、状态、并发和软删除规则；
- 云函数动作、请求/响应 DTO、错误码、权限和幂等契约；
- 前端 Repository 迁移方式，以及云端 DTO 到当前页面类型的映射；
- 初始化、发布、备份、回滚、测试、任务依赖和验收标准。

若本文档与《家庭菜单微信小程序技术文档》在首期后端范围上不一致，以本文档为本次后端实施依据。

### 1.1 MVP 范围

本期包含：

- 微信身份登录与用户首次初始化；
- 创建家庭、查询当前家庭和有效成员；
- 家庭菜谱新增、编辑、软删除、详情、分页和搜索；
- 周菜单查询、添加菜品和移除菜品；
- 投票创建、投票提交和结果查询；
- 根据周菜单生成购物清单，手动新增、勾选和清除已完成项；
- 查询和更新当前成员的饮食偏好；
- 幂等记录、关键操作日志、三环境、备份和回滚流程。

### 1.2 本期明确不做

- 成员邀请、加入、移除、退出和管理员转移的产品流程；
- 用餐反馈、图片上传、账号注销和复杂审计管理页面；
- 把当前 `store.ts` 中的种子菜谱、成员、菜单或购物清单迁移到云端；
- 同期建设独立 Node.js 服务、PostgreSQL、消息队列或全文检索服务；
- 营养分析、推荐算法、跨家庭共享和第三方菜谱同步。

当前创建家庭时只创建本人对应的管理员成员记录。后续成员邀请仍复用 `families` 与 `family_members` 模型，不需要改变本期 API 的家庭隔离方式。

### 1.3 实施原则

1. 页面不直接调用 CloudBase 数据库，只依赖 Repository 接口。
2. 云函数只从可信服务端上下文取得 OpenID，不接受客户端传入 OpenID 作为身份凭据。
3. 所有家庭业务资源都带 `familyId`，每次访问都重新验证有效成员关系。
4. 服务端负责写入时间、身份、家庭归属和审计字段，客户端不得覆盖。
5. 所有写操作都带 `requestId`，重试不能制造重复资源或重复副作用。
6. 数据库模型与当前页面展示模型分离，通过 DTO Mapper 兼容现有 `Recipe`、`MenuDay`、`ShoppingItem` 和 `AppState`。
7. CloudBase SDK 只存在于适配层，领域服务和 Repository 接口保持平台无关，以保留迁移到 Node.js + PostgreSQL 的可能。

## 2. 总体架构与工程边界

### 2.1 逻辑架构

```text
微信小程序页面
    |
    v
应用 Store / Use Case（加载、刷新、错误状态）
    |
    v
Repository 接口
    |-------------------------|
    v                         v
LocalRepository         CloudRepository
wxStorage 演示实现      wx.cloud.callFunction
                              |
                              v
CloudBase 云函数入口（按领域动作路由）
    |
    +-- 认证上下文 / 参数校验 / requestId / 错误映射
    |
    v
领域服务（家庭、菜谱、菜单、投票、购物、偏好）
    |
    v
数据访问层（CloudBase Repository 实现）
    |
    +-- CloudBase 文档数据库
    +-- CloudBase 日志与监控
    +-- 云存储（预留，本期不接图片）
```

### 2.2 各层职责

| 层 | 职责 | 禁止事项 |
| --- | --- | --- |
| 小程序页面 | 渲染、表单、加载/空/错误/冲突状态、触发用例 | 直接查数据库、拼 `familyId` 做权限判断、保存完整 `AppState` 到云端 |
| 应用 Store / Use Case | 组合多个 Repository 结果、管理页面缓存和重试 | 包含 CloudBase 查询语句 |
| Repository 接口 | 定义前端所需用例和稳定返回类型 | 暴露 CloudBase SDK 类型 |
| CloudRepository | 调云函数、附加 `requestId`、DTO 映射、错误转换 | 信任客户端身份字段、静默吞掉冲突 |
| 云函数入口 | 取得身份、校验动作和参数、调用领域服务、统一响应 | 在入口内堆积具体数据库查询 |
| 领域服务 | 执行业务规则、权限、事务、幂等、乐观锁 | 依赖页面字段或 WXML 展示结构 |
| 数据访问层 | 集合查询、索引友好查询、事务封装、数据映射 | 绕过 `familyId` 或成员校验访问家庭资源 |
| 数据库/日志 | 持久化、唯一约束、索引、审计和故障定位 | 向客户端开放家庭集合的直接读写权限 |

### 2.4 模块依赖规则

- `domain` 不依赖 CloudBase SDK、`wx` 或页面模型。
- `services` 只依赖领域类型和抽象 Repository。
- CloudBase Repository 实现依赖 SDK，但其返回值必须转换为领域对象。
- 云函数入口可依赖认证、校验、领域服务和统一响应，不能被领域层反向依赖。
- 小程序 `models/types.ts` 可以暂时保留展示字段；远程 DTO 必须放在独立文件中。
- `familyId` 可以作为资源定位参数传入，但不能作为已授权的证明；鉴权始终使用服务端查到的成员关系。
- 未来 Node.js 服务只需替换传输层、身份适配和数据访问层，不改变领域用例和客户端 Repository 方法语义。

## 3. CloudBase 环境、配置与认证

### 3.1 账号和平台准备

按以下顺序准备，任何真实 ID 或密钥不得写入本文档或 Git：

1. 完成正式微信小程序主体、AppID、开发者和发布成员配置。
2. 在微信开发者工具中用正式 AppID 打开项目，确认基础库版本满足云开发要求。
3. 在同一受控主体下创建独立 `dev`、`test`、`prod` CloudBase 环境。
4. 将小程序项目绑定到对应环境，并验证 `wx.cloud.init` 和最小登录云函数。
5. 分别创建数据库集合、索引、环境变量、日志策略和备份策略。
6. 为开发、测试、生产发布设置不同权限组；生产发布要求审批，日常开发账号不得直接修改生产数据。

### 3.2 三环境规则

| 环境 | 用途 | 数据 | 访问和发布 |
| --- | --- | --- | --- |
| `dev` | 本地开发、接口联调 | 可重置的人工数据，不包含真实生产数据 | 开发者可部署函数和重建数据 |
| `test` | 自动化、回归、验收、并发测试 | 固定测试夹具，测试前后可清理 | 测试/发布账号，版本候选部署 |
| `prod` | 正式用户 | 真实数据 | 最小权限、审批发布、备份、告警和操作留痕 |

三环境必须使用不同的 CloudBase 环境 ID、数据库、日志、函数配置和幂等记录。禁止通过集合字段模拟环境隔离，也禁止把生产数据复制到开发环境排查问题。

### 3.3 配置注入

小程序只保存非敏感配置，例如逻辑环境名、CloudBase 环境 ID 和接口版本：

```ts
export interface PublicRuntimeConfig {
  stage: 'dev' | 'test' | 'prod'
  cloudEnvId: string
  apiVersion: 'v1'
  repositoryMode: 'local' | 'cloud'
}
```

服务端配置通过 CloudBase 环境变量或受控配置服务注入，例如日志级别、幂等保留天数、最大分页大小。AppSecret、服务账号凭据和数据库管理密钥不得进入小程序包、仓库或普通日志。

建议构建产物显式选择环境，生产构建强制校验 `stage=prod`、`repositoryMode=cloud`，避免发布时连到 `dev` 或本地仓库。

### 3.4 登录和用户初始化

`auth.login` 流程：

1. 小程序调用登录云函数，不传 OpenID。
2. 云函数从 CloudBase 服务端上下文取得可信 OpenID；取不到时返回 `UNAUTHENTICATED`。
3. 用 OpenID 查询 `users`；不存在则创建，存在则更新 `lastLoginAt`。
4. 查询该用户有效的 `family_members`，再加载家庭摘要和本人偏好摘要。
5. 返回用户、当前家庭和引导状态。无家庭时 `family=null`，页面进入创建家庭流程。

昵称不应假设可从登录过程自动取得。首次登录可使用安全默认展示名，用户在引导页输入的名称经 `auth.updateProfile` 或创建家庭请求一并更新。任何客户端传入的 `userId`、`memberId` 或 OpenID 都不能替代服务端身份。

### 3.5 服务端认证上下文

所有家庭云函数在执行业务前构造：

```ts
interface AuthContext {
  requestId: string
  openid: string
  userId: string
  member: {
    id: string
    familyId: string
    role: 'owner' | 'member'
    status: 'active'
  } | null
}
```

公共中间件按“取得 OpenID -> 查用户 -> 查有效成员 -> 校验角色 -> 校验资源家庭归属”的顺序执行。成员状态不能只在登录时缓存；被移除后，下一次请求必须立即失去权限。

## 4. 数据库通用规范

### 4.1 命名、ID 和时间

- 数据库存储使用 CloudBase 原生 `_id`；服务端响应统一映射为 `id`。
- 外键字段使用字符串 `_id`，例如 `familyId`、`userId`、`recipeId`。
- 业务时间点使用数据库日期类型并由服务端写入，统一表达绝对时间。
- `weekStart` 和菜单 `date` 使用 `YYYY-MM-DD`，语义是家庭时区下的日历日期；家庭时区本期默认 `Asia/Shanghai`。
- 客户端只负责本地化展示，不得用客户端时钟写 `createdAt`、`updatedAt`、`checkedAt` 或投票截止状态。
- 文档增加 `schemaVersion`，首版为 `1`，用于兼容迁移。

### 4.2 家庭隔离和审计字段

除 `users`、`idempotency_records` 外，所有家庭业务集合都必须包含 `familyId`。所有写入资源至少包含：

```text
familyId, createdAt, createdBy, updatedAt, updatedBy, schemaVersion
```

读取资源时必须同时满足：

1. 当前用户存在；
2. 当前用户在 `family_members` 中有 `status=active` 的关系；
3. 查询条件显式包含该成员的 `familyId`；
4. 根据动作通过角色或资源所有权检查。

仅凭资源 ID 查询后再判断家庭归属容易产生越权遗漏，应优先使用 `{ _id: resourceId, familyId: context.member.familyId }` 作为数据库条件。

### 4.3 软删除和历史快照

- `recipes` 使用软删除：设置 `deletedAt`、`deletedBy`，普通查询固定过滤 `deletedAt=null`。
- 菜单条目和投票候选必须保存菜谱快照，至少包含 `recipeId`、`name`、`category`、`ingredients`。
- 菜谱删除或后续编辑不能改写历史菜单快照，也不能导致历史购物清单无法解释。
- 其他本期集合不提供用户删除动作；清除购物项是从活动列表移除并写操作日志，不等同于删除家庭历史。

### 4.4 索引和查询规则

- 每个线上查询必须有对应索引；禁止对家庭大集合执行无边界正则或全表扫描。
- 唯一索引是业务约束的一部分，服务层检查用于友好报错，不能替代数据库约束。
- 若目标 CloudBase 版本不支持所需的部分唯一索引，则采用“单文档状态更新”或事务锁记录，不得降级为仅客户端检查。
- 索引脚本必须可重复执行，并在 `dev/test/prod` 运行同一版本。
- 上线前用 `verify-environment` 校验集合、索引名、唯一性和索引字段顺序。

## 5. 集合设计

### 5.1 `users`

| 字段 | 类型 | 必填/默认 | 规则 |
| --- | --- | --- | --- |
| `_id` | string | 必填 | 用户内部 ID |
| `openid` | string | 必填 | 当前小程序唯一身份，只允许服务端写入 |
| `displayName` | string | 默认“微信用户” | 1-40 字符，去除首尾空格 |
| `avatarUrl` | string/null | 默认 `null` | 本期可不采集 |
| `status` | enum | 默认 `active` | `active` / `disabled` |
| `lastLoginAt` | datetime | 必填 | 每次成功登录由服务端更新 |
| `createdAt` | datetime | 必填 | 服务端时间 |
| `updatedAt` | datetime | 必填 | 服务端时间 |
| `schemaVersion` | integer | 默认 `1` | 数据版本 |

索引：

- `uniq_users_openid`：`openid` 唯一；
- `idx_users_status_updated`：`status, updatedAt`。

主要查询：按 OpenID 登录初始化；按 `_id` 加载当前用户。本集合不返回 OpenID 给页面。

### 5.2 `families`

| 字段 | 类型 | 必填/默认 | 规则 |
| --- | --- | --- | --- |
| `_id` | string | 必填 | 家庭 ID |
| `familyId` | string | 必填 | 与 `_id` 相同，满足家庭集合统一隔离约定 |
| `name` | string | 必填 | 1-40 字符 |
| `timezone` | string | 默认 `Asia/Shanghai` | 必须来自服务端白名单 |
| `weekStartsOn` | integer | 默认 `1` | `1` 表示周一，本期固定 |
| `status` | enum | 默认 `active` | `active` / `archived` |
| `createdAt/createdBy` | datetime/string | 必填 | 创建人是当前用户 |
| `updatedAt/updatedBy` | datetime/string | 必填 | 服务端维护 |
| `schemaVersion` | integer | 默认 `1` | 数据版本 |

索引：

- `_id` 原生唯一；
- `idx_families_status_updated`：`status, updatedAt`。

主要查询：创建家庭后按 ID 返回摘要；当前家庭必须通过有效 `family_members` 关系间接查询，不允许按名称枚举家庭。

### 5.3 `family_members`

| 字段 | 类型 | 必填/默认 | 规则 |
| --- | --- | --- | --- |
| `_id` | string | 必填 | 成员关系 ID |
| `familyId` | string | 必填 | 家庭隔离键 |
| `userId` | string | 必填 | 用户 ID |
| `role` | enum | 必填 | `owner` / `member` |
| `status` | enum | 默认 `active` | `active` / `removed` / `left` |
| `displayName` | string | 必填 | 家庭内显示名，1-40 字符 |
| `joinedAt` | datetime | 必填 | 服务端时间 |
| `endedAt` | datetime/null | 默认 `null` | 移除或退出时间 |
| `createdAt/createdBy` | datetime/string | 必填 | 服务端维护 |
| `updatedAt/updatedBy` | datetime/string | 必填 | 服务端维护 |
| `schemaVersion` | integer | 默认 `1` | 数据版本 |

索引：

- `uniq_members_family_user`：`familyId, userId` 唯一；后续重新加入时更新同一关系记录；
- `idx_members_user_status`：`userId, status`；
- `idx_members_family_status`：`familyId, status, joinedAt`。

主要查询：当前用户的有效家庭；家庭有效成员列表；每个家庭业务请求的成员鉴权。本期一个用户只允许一个 `active` 家庭关系，创建家庭前由服务层检查。

### 5.4 `recipes`

| 字段 | 类型 | 必填/默认 | 规则 |
| --- | --- | --- | --- |
| `_id` | string | 必填 | 菜谱 ID |
| `familyId` | string | 必填 | 家庭隔离键 |
| `name` | string | 必填 | 1-80 字符 |
| `searchName` | string | 必填 | 服务端生成的标准化搜索名 |
| `category` | string | 必填 | 1-30 字符，本期兼容现有中文分类 |
| `durationMinutes` | integer | 默认 `20` | 1-1440 |
| `difficulty` | enum | 默认 `easy` | `easy` / `medium` / `hard` |
| `note` | string | 默认空字符串 | 最长 1000 字符 |
| `ingredients` | array | 必填 | 1-100 项 |
| `ingredients[].name` | string | 必填 | 展示名称，1-50 字符 |
| `ingredients[].normalizedName` | string | 必填 | 服务端标准化名称 |
| `ingredients[].quantity` | number | 必填 | 大于 0，最多 3 位小数 |
| `ingredients[].unit` | string | 必填 | 标准单位，1-12 字符 |
| `createdAt/createdBy` | datetime/string | 必填 | 服务端维护 |
| `updatedAt/updatedBy` | datetime/string | 必填 | 服务端维护 |
| `deletedAt/deletedBy` | datetime/string/null | 默认 `null` | 软删除字段 |
| `schemaVersion` | integer | 默认 `1` | 数据版本 |

索引：

- `idx_recipes_family_active_updated`：`familyId, deletedAt, updatedAt, _id`；
- `idx_recipes_family_category_active`：`familyId, category, deletedAt, updatedAt`；
- 若 CloudBase 已启用受支持的文本检索能力，建立 `searchName` 搜索索引；否则 MVP 使用“标准化前缀 + 游标”查询，并限制关键字长度，禁止任意正则。

## 6. 云函数与公共接口契约

### 6.1 云函数划分

按领域部署 7 个云函数：`auth`、`family`、`recipe`、`menu`、`vote`、`shopping`、`preference`。每个函数用 `action` 路由本领域动作，例如：

```json
{
  "action": "recipe.create",
  "requestId": "req_01J...",
  "payload": {}
}
```

这样既避免为每个小动作创建过多函数，也能保持领域隔离。动作名进入日志、幂等键和权限矩阵后不得随意修改。

### 6.2 统一响应

成功：

```json
{
  "ok": true,
  "data": {},
  "requestId": "req_01J..."
}
```

失败：

```json
{
  "ok": false,
  "error": {
    "code": "VERSION_CONFLICT",
    "message": "菜单已被其他成员更新，请刷新后重试",
    "details": { "currentVersion": 5 }
  },
  "requestId": "req_01J..."
}
```

`message` 可直接展示但必须是安全文案；堆栈、数据库错误和内部集合结构只写服务端日志。生产环境不返回调试详情。

### 6.3 通用请求规则

- 写动作必须带 `requestId`；读动作可以带，未带时服务端生成并返回。
- `requestId` 在一次用户意图重试中保持不变，用户再次主动操作必须生成新值。
- 分页统一使用 `{pageSize, cursor}`，`pageSize` 默认 20、最大 50。
- 游标由服务端生成，是不透明字符串；客户端不得解析或拼装。
- ID、枚举、字符串长度、数组长度、数字范围和日期格式都在云函数入口校验。
- 服务端对可写字段使用白名单，忽略字段不是安全策略；出现未知敏感字段应返回 `VALIDATION_ERROR`。
- 所有日期范围和截止状态都以服务端时间及家庭时区计算。

### 6.4 错误码

| code | HTTP 类比 | 使用场景 | 前端处理 |
| --- | --- | --- | --- |
| `UNAUTHENTICATED` | 401 | 无可信微信身份或用户禁用 | 回登录/重试，不展示家庭数据 |
| `FAMILY_REQUIRED` | 409 | 当前用户还没有家庭 | 进入创建家庭引导 |
| `NOT_FAMILY_MEMBER` | 403 | 无有效成员关系或已被移除 | 清空家庭缓存并返回引导页 |
| `FORBIDDEN` | 403 | 已登录但角色无权执行动作 | 提示无权限，刷新权限状态 |
| `VALIDATION_ERROR` | 400 | 参数、长度、枚举或字段错误 | 标注表单字段，不自动重试 |
| `NOT_FOUND` | 404 | 资源不存在、已删除或不属于当前家庭 | 返回列表并刷新 |
| `VERSION_CONFLICT` | 409 | 菜单或购物清单版本过期 | 拉取最新数据，让用户确认后重做 |
| `VOTE_ALREADY_CAST` | 409 | 不同请求再次投同一投票 | 展示已有选择和当前结果 |
| `POLL_CLOSED` | 409 | 投票已截止/取消 | 刷新投票结果 |
| `IDEMPOTENCY_CONFLICT` | 409 | 同一 requestId 携带不同参数 | 记录客户端错误并生成新的用户意图 |
| `REQUEST_IN_PROGRESS` | 409 | 同一幂等请求正在处理 | 短暂退避后用相同 requestId 重试 |
| `RATE_LIMITED` | 429 | 超出限流 | 延迟重试并提示稍后再试 |
| `INTERNAL_ERROR` | 500 | 未知系统错误 | 展示通用提示和 requestId |

跨家庭资源 ID 对外统一返回 `NOT_FOUND`，避免泄露资源是否存在；服务端仍记录 `denied` 操作日志。

### 6.6 幂等执行模板

所有写动作按以下顺序：

1. 验证身份和基础请求格式；
2. 以 `userId + action + requestId` 尝试创建 `processing` 幂等记录；
3. 若记录已存在，比较 `requestHash`：相同则重放结果或返回处理中，不同则报冲突；
4. 执行成员权限检查和领域事务；
5. 保存成功响应摘要，并把记录置为 `succeeded`；
6. 对可稳定重放的业务错误记录 `failed + errorCode`；系统临时错误不伪装成业务成功；
7. 写操作日志并返回统一响应。

资源写入和幂等成功标记应尽可能放在同一事务中。若平台限制导致无法原子覆盖全部集合，资源本身必须携带可追踪的 `createdRequestId`，并提供故障恢复扫描，避免“资源已创建但幂等记录未成功”的重复创建窗口。

## 7. DTO 与当前前端模型的转换

### 7.1 Repository 接口建议

```ts
interface FamilyMenuRepository {
  login(): Promise<SessionView>
  createFamily(input: CreateFamilyInput): Promise<FamilyView>
  getCurrentFamily(): Promise<FamilyView>

  listRecipes(input: RecipeQuery): Promise<CursorPage<Recipe>>
  getRecipe(id: string): Promise<Recipe>
  createRecipe(input: RecipeDraft, requestId: string): Promise<Recipe>
  updateRecipe(id: string, patch: RecipePatch, requestId: string): Promise<Recipe>
  deleteRecipe(id: string, requestId: string): Promise<void>

  getWeekMenu(weekStart: string): Promise<WeekMenuView>
  addRecipeToMenu(input: AddMenuItemInput, requestId: string): Promise<WeekMenuView>
  removeRecipeFromMenu(input: RemoveMenuItemInput, requestId: string): Promise<WeekMenuView>

  createPoll(input: CreatePollInput, requestId: string): Promise<PollView>
  castVote(input: CastVoteInput, requestId: string): Promise<PollResultView>
  getPollResult(pollId: string): Promise<PollResultView>

  getShoppingList(weekStart: string): Promise<ShoppingListView | null>
  generateShoppingList(input: GenerateShoppingInput, requestId: string): Promise<ShoppingListView>
  updateShoppingItem(input: ShoppingItemMutation, requestId: string): Promise<ShoppingListView>

  getMyPreference(): Promise<PreferenceView>
  updateMyPreference(input: PreferenceInput, requestId: string): Promise<PreferenceView>
}
```

页面逐步改为使用这些用例。`LocalRepository` 通过现有同步 `store.ts` 返回 `Promise.resolve`，`CloudRepository` 调用云函数；因此可以按模块切换，不必一次重写所有页面。

### 7.2 `Recipe` 映射

当前 `Recipe` 展示字段与远程菜谱的映射：

| 当前字段 | 远程来源/转换 |
| --- | --- |
| `id` | 数据库 `_id` -> DTO `id` |
| `name` | `name` |
| `initial` | 客户端由 `name.slice(0, 1)` 计算，不入库 |
| `category` | `category`，本期保留中文值兼容页面筛选 |
| `duration` | `durationMinutes` |
| `difficulty` | `easy/medium/hard` 映射为“简单/适中/困难” |
| `tone` | 客户端按 ID 稳定散列到现有色板，不入库 |
| `note` | `note` |
| `ingredients[].amount` | `ingredients[].quantity` |
| `ingredients[].unit/name` | 同名字段 |

`normalizedName` 是后端合并字段，不需要进入当前页面 `Ingredient`。

### 7.3 `MenuDay` 映射

远程周菜单的 `days[]` 映射为当前 `MenuDay[]`：

- `key`：使用 `date`；
- `weekday`、`dateLabel`：客户端按家庭时区和日期生成；
- `breakfast/lunch/dinner`：当前类型只接收菜谱 ID，因此从菜单条目提取 `recipeId`；
- 页面渲染优先使用菜单条目中的 `recipeSnapshot`，不能只从活动菜谱列表反查，否则软删除菜谱会从历史菜单消失；
- `version`、`menuId` 和 `itemId` 放入新的 `WeekMenuView`，不要硬塞进 `MenuDay`。

菜单页实施远程接入时应同步把 `MealView.items` 改为菜单条目视图，以支持精确移除和历史快照。

### 7.4 `ShoppingItem` 映射

| 当前字段 | 远程来源/转换 |
| --- | --- |
| `id` | `items[].id` |
| `name` | `items[].name` |
| `amount` | `items[].quantity` |
| `unit` | `items[].unit` |
| `checked` | `items[].checked` |
| `category` | `items[].category` |

购物页需要额外保存清单 `id` 和 `version`，每次写入成功后用服务端返回的新版本替换本地版本。

### 7.5 `AppState` 的远程替代

远程模式不保存或上传单一 `AppState` 文档。页面兼容状态由多个服务端资源组合：

| `AppState` 字段 | 远程来源 |
| --- | --- |
| `onboarded` | `auth.login.onboardingRequired === false` |
| `userName` | `users.displayName` |
| `familyName` | `families.name` |
| `members` | `family.current.members[].displayName` |
| `recipes` | `recipe.list` 分页结果 |
| `weekMenu` | `menu.week` 映射结果 |
| `shoppingItems` | `shopping.get` 的 `items` |
| `votedRecipeId` | 当前开放投票的 `currentVote.candidateRecipeId` |
| `spicyLevel` | `preferences.spicyLevel` |
| `avoidFood` | `avoidFoods.join('、')`，提交时再拆分和清洗 |

首次切到远程模式时不读取 `family-menu-state-v1` 作为上传源。可以保留缓存供回退到本地模式，但云端页面必须以登录响应和远程查询为准。

### 7.6 Repository 模式开关

迁移期支持：

- `local`：全部使用现有本地演示数据；
- `cloud`：已迁移模块必须使用云端，禁止缺失接口时静默回落到本地；
- 开发阶段可在 Repository 工厂内按模块配置，但生产构建只允许全部 `cloud`。

远程失败不能自动读取演示种子数据冒充真实家庭数据。离线时展示最近一次只读缓存和“数据可能不是最新”状态，写操作保留表单并提示重试。

## 8. 权限、并发与安全

### 8.1 权限矩阵

| 动作 | 访客/无家庭 | 家庭成员 | 家庭管理员 |
| --- | --- | --- | --- |
| 登录、更新本人名称 | 允许 | 允许 | 允许 |
| 创建家庭 | 允许（仅无家庭） | 禁止 | 禁止 |
| 查询当前家庭/成员 | 禁止 | 允许 | 允许 |
| 菜谱查询/新增/编辑 | 禁止 | 允许 | 允许 |
| 删除本人创建的菜谱 | 禁止 | 允许 | 允许 |
| 删除他人菜谱 | 禁止 | 禁止 | 允许 |
| 周菜单查询/增删菜品 | 禁止 | 允许 | 允许 |
| 创建投票 | 禁止 | 禁止 | 允许 |
| 投票/查看结果 | 禁止 | 允许 | 允许 |
| 购物清单生成和维护 | 禁止 | 允许 | 允许 |
| 查询/更新本人偏好 | 禁止 | 允许 | 允许 |
| 查询/更新他人偏好 | 禁止 | 禁止 | 禁止 |

页面隐藏按钮只改善体验，不能替代服务端权限检查。

### 8.2 家庭隔离中间件

公共 `requireActiveMember` 中间件输出已验证的 `familyId`、`memberId` 和角色。领域查询必须从该上下文取家庭 ID，而不是直接使用 `payload.familyId`。对确需传资源 ID 的动作，数据库条件同时包含资源 ID 和上下文家庭 ID。

### 8.3 菜单乐观锁

添加和移除菜单条目必须携带 `expectedVersion`：

1. 查询 `{familyId, weekStart}` 当前菜单；
2. 检查版本与请求一致；
3. 以 `{_id, familyId, version: expectedVersion}` 为条件更新内容并执行 `version + 1`；
4. 更新数为 0 时重新读取当前版本并返回 `VERSION_CONFLICT`；
5. 前端展示最新菜单，要求用户重新确认操作。

不得用“最后写入覆盖”处理并发菜单修改。

### 8.4 投票并发

- 先验证投票属于当前家庭、状态开放、未截止、候选项有效；
- 服务层预查用于返回友好错误；
- 插入 `votes` 时由 `pollId + voterMemberId` 唯一索引最终防重；
- 唯一键冲突转换为 `VOTE_ALREADY_CAST`，不能返回数据库原始错误；
- 票数从 `votes` 聚合，不在 `polls` 中维护易漂移的客户端可写计数。

### 8.5 事务边界

以下操作必须使用数据库事务或等价原子方案：

- 创建家庭：家庭记录 + 管理员成员记录 + 幂等结果；
- 提交投票：投票记录 + 幂等结果；
- 首次创建周菜单或购物清单时的唯一键竞争；
- 重新生成购物清单：校验菜单版本 + 替换菜单来源项 + 清单版本递增；
- 任何未来涉及成员角色成对变化的操作。

事务内仍需处理唯一索引竞争和重试上限。

### 8.6 参数和内容安全

- 使用统一 schema 校验器；所有对象拒绝原型链危险键和未声明字段。
- 字符串先检查类型和长度，再做 trim/标准化；不能先截断后静默接受。
- 食材数量只接受有限正数，拒绝 `NaN`、无穷大和超范围小数。
- 日期必须严格解析，周起始必须是周一，菜单日期必须属于请求周。
- 每个云函数设置请求体上限、超时和合理的数据库操作次数。
- 对登录、写菜谱、投票和购物清单生成设置按用户/家庭的限流。
- 数据库安全规则默认拒绝客户端直接访问业务集合，只允许云函数受信环境访问。
- 日志中对用户输入只记录长度、数量或字段名，不记录完整内容。

## 9. 初始化、迁移与发布

### 9.1 首次初始化顺序

1. 准备正式 AppID、CloudBase 管理员和发布账号。
2. 创建 `dev/test/prod` 环境并记录在受控配置中。
3. 部署最小 `auth.login`，验证三环境身份上下文互相隔离。
4. 创建 11 个集合并设置“客户端默认不可直接读写”。
5. 执行版本化索引脚本，检查所有唯一索引和字段顺序。
6. 注入服务端环境变量，配置函数超时、内存、日志和告警。
7. 部署云函数共享基础层，再按认证、家庭、菜谱、菜单、投票、购物、偏好顺序部署。
8. 在 `dev` 运行冒烟测试，在 `test` 运行全量集成与隔离测试。
9. 配置 `prod` 备份、恢复演练计划和发布审批后，才允许小程序生产版本切到云端。

### 9.2 本地数据处理

- 不上传 `family-menu-state-v1` 中的任何演示数据。
- 切换云端后，以 `auth.login` 返回状态覆盖页面会话；旧缓存可以直接忽略。
- 为避免用户误以为演示数据丢失，开发/体验版切换时显示一次说明；正式环境上线前不应产生需要迁移的真实本地用户数据。
- 云端稳定后再删除种子数据和“重置体验数据”入口；删除前保留 `LocalRepository` 供开发演示。

### 9.3 分阶段迁移

| 阶段 | 云端能力 | 前端切换 | 退出条件 |
| --- | --- | --- | --- |
| A 认证与家庭 | `auth`、`family`、用户/家庭/成员集合 | 启动和 onboarding 改走 Repository | 新用户可登录、创建家庭、重启后恢复会话 |
| B 菜谱 | 菜谱 CRUD、分页、搜索、软删除 | 菜谱列表和编辑页改走云端 | 不再从 `AppState.recipes` 读写真实数据 |
| C 菜单与投票 | 周菜单、版本锁、投票和唯一约束 | 首页、菜单页、投票页改走云端 | 并发冲突和重复投票用例通过 |
| D 购物与偏好 | 清单生成/维护、偏好接口 | 购物页、个人页改走云端 | 闭环验收、三环境和运维验收通过 |

每个阶段只允许显式开关切换；不能在同一业务数据上同时写本地和云端，也不做双写。

### 9.4 数据库兼容变更

- 所有 schema 和索引变更以版本化脚本提交评审。
- 优先“先加后用”：先增加可选字段/索引并部署兼容后端，再发布使用它的客户端。
- 字段改名先双读或服务端兼容旧字段，至少跨一个已发布小程序版本后再清理。
- 不在发布窗口直接执行不可逆批量删除；大批量回填先在 `test` 验证耗时、失败恢复和限速。
- 每次部署记录 `apiVersion`、函数版本、schema 版本和索引版本。

### 9.5 发布、灰度和回滚

发布顺序：

1. 备份生产数据库并确认最近一次备份可用；
2. 执行向后兼容的集合/索引变更；
3. 部署兼容旧客户端的新云函数版本；
4. 在生产执行只读冒烟和受控测试账号写入；
5. 发布小程序灰度版本；
6. 观察登录、家庭创建、接口错误率、P95、冲突率和关键操作成功率；
7. 扩大灰度并最终全量。

函数回滚使用上一稳定版本；小程序回滚使用上一审核通过版本或关闭远程功能开关。数据库回滚优先使用向前修复脚本，只有数据损坏且评估影响后才从备份恢复。恢复必须记录 RPO/RTO、影响家庭范围和对账步骤。

建议目标：每日自动备份，RPO 不超过 24 小时，RTO 不超过 4 小时；至少每季度在隔离环境完成一次恢复演练。

## 11. 测试方案

### 11.1 单元测试

- DTO Mapper：Recipe 枚举/字段映射、MenuDay 日期、ShoppingItem 数量字段、AppState 组合；
- 权限判断：访客、成员、管理员、创建者和已失效成员；
- 食材标准化：空格、大小写、常见别名、单位、不可换算单位和小数；
- 食材合并：相同标准名+单位求和，不同单位不合并，来源菜谱去重；
- 菜单日期：周一计算、跨月/跨年、家庭时区；
- 菜单版本：期望版本命中和冲突；
- requestHash：对象字段顺序变化不改变哈希，业务参数变化必须改变哈希；
- 游标编码解码和稳定排序。

### 11.2 云函数集成测试

- 登录只能使用服务端 OpenID，客户端伪造身份字段无效；
- 用户首次创建与重复登录；
- 家庭创建事务中途失败后无孤儿家庭/成员；
- 每个写接口的缺字段、未知字段、超长字符串、超大数组和非法数字；
- 相同 `requestId` 重试、不同参数复用 requestId、处理中重试；
- 菜谱软删除、删除权限、删除后新菜单拒绝引用；
- 菜单首次创建唯一竞争、版本冲突和历史快照；
- 投票已截止、候选无效、重复投票和唯一索引冲突；
- 购物清单相同版本重复生成、菜单变更后生成、手动项保留；
- 偏好只能读写本人。

### 11.3 数据隔离与安全测试

为家庭 A、家庭 B 和已移除成员分别准备账号，逐个接口验证：

- 在 payload 中伪造家庭 B 的 `familyId`；
- 使用家庭 B 的 recipe/menu/poll/list ID；
- 使用存在但已软删除的菜谱 ID；
- 登录后把成员状态改为 `removed`，不重新登录直接发请求；
- 普通成员执行管理员动作；
- 客户端直接访问数据库集合；
- 日志中搜索 OpenID、访问凭据和完整偏好，结果必须为空。

对外错误不得暴露跨家庭资源存在性。

### 11.4 并发与幂等测试

- 两名成员同时基于相同版本修改周菜单：仅一个成功，另一个版本冲突；
- 同一成员用两个并发请求投票：最终只有一条 `votes`；
- 相同 requestId 并发创建菜谱/家庭：最终只有一个资源；
- 两个请求同时首次生成同一周购物清单：最终只有一个活动清单；
- 两名成员同时勾选不同购物项：客户端可在冲突后刷新重试，不能静默覆盖；
- 同一菜单版本重复生成清单：返回相同清单，不重复累计数量。

### 11.5 前端集成测试

覆盖完整闭环：首次登录 -> 创建家庭 -> 新增/编辑/删除菜谱 -> 周菜单添加/移除 -> 管理员创建投票 -> 成员投票 -> 生成购物清单 -> 勾选/新增/清除 -> 更新偏好。

每个页面同时覆盖 `loading`、`empty`、`offline`、`forbidden`、`validation error`、`version conflict` 和 `internal error`。写失败后表单和用户输入不能丢失；不能用演示数据填充远程空状态。

### 11.6 环境和运维测试

- `dev/test/prod` 的环境 ID、集合数量、索引版本、函数变量互相独立；
- 测试账号无法部署生产，普通开发账号无法浏览生产数据；
- 测试备份创建、恢复到隔离环境、数据抽样校验和恢复耗时；
- 云函数上一版本回滚、小程序回滚和功能开关切换；
- 告警能带 requestId 定位错误，但不包含敏感身份数据；
- 生产构建检查能阻止 `repositoryMode=local` 或非生产环境 ID。

## 12. 验收标准

### 12.1 功能与数据

- [ ] 新用户能以微信身份登录，首次访问只创建一条 `users` 记录。
- [ ] 无家庭用户能创建家庭，并原子创建管理员成员关系。
- [ ] 重启小程序后可恢复当前用户和家庭，不依赖本地演示 `AppState`。
- [ ] 家庭成员能完成菜谱新增、编辑、软删除、详情、分页和搜索。
- [ ] 删除菜谱后不能用于新菜单，但历史菜单仍显示菜谱快照。
- [ ] 周菜单能添加和移除菜品，所有修改递增 `version`。
- [ ] 管理员能创建投票，成员能投票并查看汇总。
- [ ] 同一成员对同一投票只能有一条有效投票记录。
- [ ] 周菜单能生成按标准食材名和单位合并的购物清单。
- [ ] 购物项新增、勾选、清除和重新生成规则符合约定。
- [ ] 成员能查询和更新自己的饮食偏好，不能访问他人偏好。

### 12.2 隔离、并发和可靠性

- [ ] 不同家庭无法读取或修改彼此任何资源。
- [ ] 成员关系失效后，无需重新登录即在下一次请求失去家庭访问权限。
- [ ] 并发修改同一周菜单时，过期请求得到 `VERSION_CONFLICT`，不会覆盖新数据。
- [ ] 并发投票不会产生重复记录或重复票数。
- [ ] 重复提交同一写请求不会创建重复家庭、菜谱、投票或购物清单。
- [ ] 同一 requestId 携带不同参数会被拒绝并记录。
- [ ] 断网、无权限、空数据、参数错误、资源删除、版本冲突和服务异常都有明确反馈与重试策略。

### 12.3 环境与运维

- [ ] `dev/test/prod` 的数据、配置、函数、日志、备份和发布权限相互隔离。
- [ ] 三环境集合和索引版本一致，生产客户端不能直接读写数据库。
- [ ] 生产有登录、家庭创建、云函数错误率、P95、投票和清单生成指标。
- [ ] 关键写操作、权限拒绝和系统异常可通过 requestId 追踪，日志不包含敏感身份数据。
- [ ] 已完成一次备份恢复和函数/小程序回滚演练，并记录 RPO/RTO。
- [ ] 当前本地演示数据没有进入云端，生产版本不再依赖 LocalRepository。

## 13. 已知风险与后续演进

| 风险 | 当前控制 | 触发后的演进 |
| --- | --- | --- |
| 周菜单单文档并发粒度较粗 | MVP 用整周 `version`，冲突后刷新重试 | 高频冲突时拆为按日期或餐次聚合 |
| 购物项嵌入数组接近文档大小/更新性能上限 | 限制 300 项并监控文档大小 | 拆出 `shopping_items` 集合 |
| CloudBase 搜索能力有限 | 标准化前缀、分类、游标和查询限制 | 引入受控全文索引服务 |
| 多环境手工配置漂移 | 版本化脚本和环境校验 | 建立完整 IaC/CI 自动部署 |
| 云函数共享代码重复打包 | 统一源码和构建产物 | 抽为工作区包或迁移云托管服务 |
| 未来多端和复杂报表增加平台耦合 | 领域服务和 Repository 不依赖 CloudBase SDK | 迁移到 Node.js API + PostgreSQL，客户端契约保持不变 |

当出现跨端统一 API、复杂统计/营养报表、强关系约束、高并发成本或 CloudBase 查询能力成为明确瓶颈时，再立项评估 Node.js + PostgreSQL。迁移时保留本文件定义的动作语义、错误码、requestId、家庭隔离和乐观锁契约，避免前端随数据库更换而重写。
