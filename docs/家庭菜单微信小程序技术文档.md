# 家庭菜单微信小程序技术文档

> 文档版本：V1.0
>
> 更新日期：2026-07-22
>
> 状态：可用于产品、设计、前端、后端和测试拆分任务

## 1. 文档目标与产品范围

本文档定义家庭菜单微信小程序首发版本的产品边界、技术架构、数据契约、业务规则、页面行为、测试和运维要求。产品以家庭为数据隔离单元，帮助成员共同完成“建家庭 -> 录入菜谱 -> 排菜单 -> 投票 -> 生成购物清单 -> 用餐反馈”的闭环。

### 1.1 首版目标

- 新用户在 3 分钟内完成微信登录、创建家庭并添加第一道菜。
- 家庭成员打开首页即可看到当天菜单和待办投票。
- 以周为单位安排菜单，并能按标准食材汇总购物清单。
- 投票、菜单和购物项在多成员并发操作下保持一致。
- 所有家庭数据严格隔离，生产环境具备日志、备份和回滚能力。

### 1.2 MVP 范围

包含：家庭创建/加入/邀请、成员与角色管理、家庭菜谱 CRUD 和搜索、日/周菜单、候选菜投票、购物清单、口味偏好/忌口/过敏、用餐反馈、图片上传、基础监控。

不包含：社区内容、商城和支付、外部菜谱平台同步、复杂营养分析、即时聊天、独立 App/Web 端。相关能力进入后续迭代路线。

### 1.3 用户角色与权限

| 角色 | 能力 | 约束 |
| --- | --- | --- |
| 家庭管理员 | 创建家庭、修改家庭设置、邀请/移除成员、转移管理员、管理全部家庭内容 | 每个家庭恰有一名有效管理员；转移后原管理员立即失效 |
| 家庭成员 | 查看菜单和菜谱、添加/编辑自己创建的菜谱、投票、维护购物清单、修改自己的偏好和反馈 | 只能访问当前所属家庭；不能管理成员和家庭设置 |
| 访客状态 | 微信登录、创建家庭、通过邀请码加入家庭 | 未加入家庭时不得读取任何家庭内容 |

管理员对成员的移除、管理员转移和家庭删除需要二次确认，并写入操作日志。

## 2. 总体架构

### 2.1 逻辑架构

```text
微信小程序
  页面层 WXML/WXSS/TypeScript
  组件层 菜单卡片、菜谱卡片、投票、食材清单
  状态层 当前用户、家庭上下文、菜单、偏好
  API 层 请求封装、鉴权、重试、错误映射
       |
CloudBase 云函数/API 服务层
  auth / family / recipe / menu / vote / shopping / preference / feedback
  参数校验、权限策略、事务/幂等、领域服务、数据访问层
       |
CloudBase MongoDB | 云存储 | 日志与监控
```

客户端保持页面、组件、状态、API、数据访问分层。云函数对外只暴露用例接口，禁止页面直接拼接数据库查询。领域服务和 Repository 接口不依赖 CloudBase SDK，以便未来迁移 Node.js 服务。

### 2.2 模块职责

| 模块 | 主要职责 | 首版交付物 |
| --- | --- | --- |
| 认证 | 微信登录、会话续期、用户注销 | `login` 云函数、用户初始化 |
| 家庭与成员 | 家庭生命周期、邀请码、角色和成员状态 | family API、权限中间件 |
| 菜谱 | 菜谱字段、图片、食材、步骤、搜索 | recipe API、图片上传策略 |
| 菜单排程 | 日/周菜单读写、近期重复提示 | menu API、日历/周视图 |
| 投票 | 候选菜、投票窗口、一人一票、结果汇总 | vote API、并发唯一约束 |
| 购物清单 | 从菜单汇总食材、勾选、清空 | shopping API、标准化合并 |
| 偏好与反馈 | 忌口、过敏、口味、餐后评分 | preference/feedback API |
| 平台能力 | 上传、日志、告警、备份 | CloudBase 环境和 CI/CD |

### 2.3 环境

- `dev`：开发者个人或共享开发环境，允许测试数据，使用独立数据库。
- `test`：验收和自动化测试环境，数据可重置，使用测试小程序 AppID。
- `prod`：正式环境，限制操作权限，启用备份、告警和灰度发布。

配置通过环境变量或 CloudBase 环境配置注入，禁止把 AppSecret、数据库密钥写入仓库。每个环境维护同名索引和 schema 版本。

## 3. 技术选型与迁移预案

### 3.1 默认技术栈

| 层 | 方案 | 选择理由 |
| --- | --- | --- |
| 客户端 | 微信原生小程序 + TypeScript | 首发平台一致，包体和启动性能可控 |
| 工程质量 | ESLint、Prettier、TypeScript strict、GitHub Actions | 统一风格并在合并前阻断类型错误 |
| UI | 自定义轻量组件，必要时引入单一组件库 | 保持包体小，贴合家庭场景交互 |
| 服务 | CloudBase 云函数或云托管 Node.js | 免运维、与微信身份和存储集成 |
| 数据库 | CloudBase MongoDB | 快速迭代嵌套食材/步骤模型 |
| 文件 | CloudBase 云存储 | 临时凭证上传，统一访问控制 |
| 登录 | 微信登录，服务端换取 OpenID/UnionID | 不在客户端保存敏感凭据 |
| 监控 | CloudBase 日志、微信小程序性能监控 | 覆盖函数错误、接口延迟、启动性能 |

### 3.2 自建 Node.js + PostgreSQL 对比

| 维度 | CloudBase | Node.js + PostgreSQL |
| --- | --- | --- |
| 上线速度 | 快，平台托管 | 需要部署、网络和数据库运维 |
| 查询与事务 | 常规家庭场景足够，复杂聚合需谨慎 | SQL、事务、报表和约束更强 |
| 成本 | 小规模按量，运维成本低 | 稳定高负载更容易做成本预测 |
| 跨端复用 | 需通过 API 规范补齐 | 天然适合 App、Web、开放 API |
| 迁移成本 | 需抽象 Repository 并导出数据 | 初期研发和运维投入更高 |

出现以下任一信号时评估迁移：跨端产品需要统一后端、复杂营养/历史报表占主要查询量、需要强事务和跨集合报表、并发或数据量超出 CloudBase 成本/性能目标，且团队具备数据库和 SRE 能力。迁移前先冻结领域接口、建立双写或离线回放方案，不能直接替换生产数据库。

## 4. 数据模型

### 4.1 通用约定

- 主键使用字符串 `id`（CloudBase 文档 `_id` 映射为 `id`），时间统一 ISO 8601 UTC，客户端按用户时区展示。
- 所有家庭数据含 `familyId`，服务端从会话和成员关系取得并校验，禁止信任客户端传入的家庭身份。
- 通用字段：`createdAt`、`updatedAt`、`createdBy`；可删除实体增加 `deletedAt`、`deletedBy`，删除采用软删除。
- 请求写操作带 `requestId`；需要重试的接口按 `(userId, requestId)` 做幂等记录。
- 枚举值在 API 文档和 TypeScript 类型中保持一致，未知枚举必须向后兼容处理。

### 4.2 `users`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 用户 ID |
| `openid` | string | 是 | 当前小程序 OpenID，唯一、不可展示 |
| `unionid` | string | 否 | 有开放平台绑定时记录 |
| `nickname` | string | 是 | 展示昵称，长度 1-40 |
| `avatarUrl` | string | 否 | 云存储或微信头像 URL |
| `status` | enum | 是 | `active` / `deleted` |
| `lastLoginAt` | datetime | 是 | 最近登录时间 |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`openid` unique、`unionid` sparse unique、`status`。注销时去标识化昵称/头像，保留满足家庭历史记录所需的匿名用户 ID。

### 4.3 `families`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 家庭 ID |
| `name` | string | 是 | 1-40 字符 |
| `ownerMemberId` | string | 是 | 当前管理员对应的成员 ID |
| `inviteCodeHash` | string | 是 | 邀请码哈希，不存明文 |
| `inviteExpiresAt` | datetime | 否 | 为空表示不失效 |
| `settings` | object | 是 | `timezone`、`weekStartsOn`、`defaultMealTypes` |
| `status` | enum | 是 | `active` / `archived` |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`status`、`ownerMemberId`。邀请码只在加入时短时返回，生成/轮换时使旧码失效。

### 4.4 `family_members`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 成员关系 ID |
| `familyId` | string | 是 | 家庭隔离键 |
| `userId` | string | 是 | 用户 ID |
| `role` | enum | 是 | `owner` / `member` |
| `status` | enum | 是 | `active` / `invited` / `removed` / `left` |
| `displayName` | string | 否 | 家庭内称呼 |
| `joinedAt`/`leftAt` | datetime | 否 | 状态变更时间 |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`(familyId,userId)` unique（仅允许一个有效关系，历史关系通过状态保留）、`familyId,status`、`userId,status`。任何家庭查询都要求 `status=active`。

### 4.5 `recipes`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 菜谱 ID |
| `familyId` | string | 是 | 家庭隔离键 |
| `name` | string | 是 | 1-80 字符 |
| `coverImage` | object | 否 | `fileId`、`width`、`height` |
| `category` | enum | 否 | `home`、`soup`、`staple`、`snack`、`other` |
| `servings` | integer | 是 | 1-20 |
| `ingredients` | array | 是 | `{name, normalizedName, usedUp}`；家常做法不记用量，`usedUp` 表示做完是否用完、下次是否要采购 |
| `steps` | array | 是 | `{order, text, imageFileId?}` |
| `tags` | string[] | 否 | 家庭自定义标签 |
| `createdBy` | string | 是 | 创建者用户 ID |
| `deletedAt`/`deletedBy` | datetime/string | 否 | 软删除字段 |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`(familyId,deletedAt,updatedAt)`、`(familyId,category,deletedAt)`；名称搜索使用前缀/全文索引能力，不能用不受控正则扫描全表。

### 4.6 `menus`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 菜单记录 ID |
| `familyId` | string | 是 | 家庭隔离键 |
| `date` | date | 是 | 家庭时区下的日期 |
| `mealType` | enum | 是 | `breakfast` / `lunch` / `dinner` / `snack` |
| `recipeIds` | string[] | 是 | 允许重复菜谱 ID |
| `note` | string | 否 | 备注 |
| `source` | enum | 是 | `manual` / `vote` |
| `createdBy` | string | 是 | 创建者 |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`(familyId,date,mealType)` unique、`(familyId,date)`。写入时校验菜谱属于同一家庭且未删除；近期 7 天重复只提示，不阻止保存。

### 4.7 `polls`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 投票主题 ID |
| `familyId` | string | 是 | 家庭隔离键 |
| `date` | date | 是 | 对应的用餐日期 |
| `mealType` | enum | 是 | `breakfast` / `lunch` / `dinner` / `snack` |
| `candidateRecipeIds` | string[] | 是 | 候选菜谱，数量 2-10 |
| `closesAt` | datetime | 是 | 截止时间，必须早于用餐开始 |
| `status` | enum | 是 | `open` / `closed` / `cancelled` |
| `createdBy` | string | 是 | 创建者用户 ID |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`(familyId,date,mealType,status)`、`(familyId,status,closesAt)`。同一家庭、日期和餐次最多一个 `open` 投票；关闭时由云函数根据截止时间或管理员操作更新状态，并可将得票第一的菜谱写入菜单（需管理员确认时仅生成推荐）。

### 4.8 `votes`

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 是 | 投票记录 ID |
| `familyId` | string | 是 | 家庭隔离键 |
| `pollId` | string | 是 | 投票主题/窗口 ID |
| `candidateRecipeId` | string | 是 | 候选菜谱 |
| `voterUserId` | string | 是 | 投票人 |
| `value` | integer | 是 | 首版固定为 `1` |
| `createdAt`/`updatedAt` | datetime | 是 | 通用时间 |

索引：`(pollId,voterUserId)` unique，`(familyId,pollId,candidateRecipeId)`。同一投票重复提交返回幂等成功或 `VOTE_ALREADY_CAST`，由前端统一展示。

### 4.9 `shopping_lists` 与条目

`shopping_lists` 字段：`id`、`familyId`、`weekStart`、`sourceMenuVersion`、`status(active/archived)`、`createdBy`、`createdAt`、`updatedAt`。索引 `(familyId,weekStart)` unique。

条目嵌入 `items` 数组（规模较大时拆为 `shopping_items`）：

```json
{
  "name": "番茄", "normalizedName": "番茄",
  "checked": false, "sourceRecipeIds": ["r1"],
  "note": "优先购买熟一点的"
}
```

只汇总菜谱中标记“会用完”（`usedUp=true`）的食材；合并键为 `normalizedName`，同名食材只列一条。`checkedAt`、`checkedBy` 用于审计。

### 4.10 `preferences` 与 `meal_feedback`

`preferences`：`id`、`familyId`、`userId`、`spicyLevel(0-3)`、`dislikes[]`、`allergies[]`、`dietGoals[]`、`notes`、时间字段。索引 `(familyId,userId)` unique。过敏原属于高敏感信息，只对本家庭成员和本人可见。

`meal_feedback`：`id`、`familyId`、`userId`（用户注销后保留匿名化 ID）、`menuId`、`rating(1-5)`、`comment`、`tags[]`、时间字段、软删除字段。索引 `(familyId,menuId,userId)` unique，允许用户更新自己的反馈。

## 5. API 与云函数契约

### 5.1 统一约定

请求通过 `wx.cloud.callFunction` 调用，服务端从 CloudBase 上下文获取用户身份。接口响应：

```json
{ "ok": true, "data": {}, "requestId": "req_123" }
```

错误响应：

```json
{
  "ok": false,
  "error": { "code": "FORBIDDEN", "message": "无权访问该家庭", "details": {} },
  "requestId": "req_123"
}
```

错误码至少包括 `UNAUTHENTICATED`、`FORBIDDEN`、`NOT_FOUND`、`VALIDATION_ERROR`、`CONFLICT`、`RATE_LIMITED`、`INTERNAL_ERROR`。客户端只展示安全的 `message`，详细堆栈只写日志。

列表接口统一接收 `page`（从 1 开始）、`pageSize`（默认 20，最大 50）、`cursor?`、`keyword?`；返回 `{items,total?,nextCursor?}`。所有写接口接受 `requestId`，重试不得产生重复资源。

权限校验顺序：身份有效 -> 家庭成员关系 `active` -> 角色权限 -> 资源 `familyId` 一致 -> 输入 schema 校验。云函数必须在服务端再次校验，不能依赖页面隐藏按钮。

### 5.2 核心接口

| 云函数/动作 | 请求要点 | 成功结果 |
| --- | --- | --- |
| `auth.login` | 微信登录上下文 | 当前用户资料和家庭摘要 |
| `family.create` | `name`、`settings`、`requestId` | 家庭、管理员成员、一次性邀请信息 |
| `family.join` | `inviteCode`、`requestId` | 当前家庭摘要；已加入时幂等 |
| `family.invite` | 管理员，`expiresInHours` | 新邀请码摘要 |
| `family.current` | 无家庭 ID | 当前有效家庭和成员 |
| `family.members` | 管理员/成员只读 | 分页成员 |
| `family.removeMember` | `memberId`、`requestId` | 成员状态变为 `removed` |
| `family.transferOwner` | `targetMemberId`、二次确认 token | 新旧角色原子变更 |
| `recipe.create/update` | 菜谱字段、`requestId` | 菜谱详情 |
| `recipe.delete` | `recipeId`、`requestId` | 软删除结果 |
| `recipe.list` | `keyword/category/cursor` | 分页菜谱 |
| `menu.week` | `weekStart` | 该周菜单和版本号 |
| `menu.upsert` | `date/mealType/recipeIds/version` | 新版本菜单；版本冲突返回 `CONFLICT` |
| `vote.createPoll` | 日期、候选菜、截止时间 | `pollId` 和候选项 |
| `vote.cast` | `pollId/candidateRecipeId/requestId` | 投票结果；唯一约束保证一票 |
| `vote.summary` | `pollId` | 各候选票数和当前用户投票 |
| `shopping.generate` | `weekStart/requestId` | 合并后的购物清单 |
| `shopping.updateItem` | `listId/itemId/checked` | 更新后的条目 |
| `shopping.clearChecked` | `listId/requestId` | 已勾选项归档或删除 |
| `preference.update` | 偏好字段 | 当前用户偏好 |
| `feedback.submit` | `menuId/rating/comment/tags/requestId` | 反馈详情 |

### 5.3 并发、幂等与版本

菜单更新携带读取时的 `version` 或 `updatedAt`，服务端使用乐观锁；冲突时返回最新数据，页面提示用户重新选择。投票依赖数据库唯一索引和幂等记录双重保护。购物清单生成按 `(familyId,weekStart,sourceMenuVersion)` 幂等，菜单变更后可显式重新生成，不自动覆盖已勾选条目。

## 6. 关键业务规则

1. 所有家庭集合查询必须带 `familyId`，且 `family_members.status=active`；被移除或退出的成员立即失去访问权。
2. 一名成员对同一 `pollId` 只能有一票；投票截止后拒绝写入。
3. 菜谱只软删除；历史菜单、投票和反馈仍可展示菜名快照。编辑菜谱不回写历史菜单。
4. 食材先标准化名称和大小写，再按 `normalizedName` 合并；不记录用量和单位，只按“是否用完”决定是否进采购单。
5. 菜单允许重复，保存时对近 7 天同餐次重复显示提示；不阻止管理员确认保存。
6. 成员退出后，历史投票/反馈保留匿名化归属；家庭成员列表不展示该用户。
7. 管理员转移在单个事务/批处理内完成，新管理员生效后原管理员所有管理 API 立即返回 `FORBIDDEN`。
8. 家庭删除先进入 `archived`，保留 30 天恢复窗口；到期由后台任务清理可删除的个人数据和文件。
9. 过敏信息默认不用于公开展示；推荐能力（后续版本）必须先过滤家庭成员过敏原。

## 7. 页面、路由与交互

### 7.1 冰箱页面与接口边界（ROBB-17）

- 沿用原生小程序 TypeScript、WXML、WXSS 和 `modules/*` 分层。首页提供入口，不增加第六个 Tab；周菜单通过 `menuId/itemId/weekStart/date/mealType` 打开做菜确认页。
- 页面只通过 `modules/fridge` 及既有 `CloudClient` 调用 `fridge` 云函数，不直接读写数据库或调用 AI。冰箱是云端家庭共享功能；本地演示模式明确提示不可用，不返回模拟库存。
- `fridge.listBatches` 返回批次；`fridge.listRecords` 使用 `cursor/pageSize` 分页；`fridge.createBatch/updateBatch/discardBatch/cook` 为写操作；`fridge.suggest` 只读库存。动作及响应对接 ROBB-16，适配层校验响应并转换中文状态、报损/消耗说明和上海时区时间。
- 录入与修改仅填写名称、可选保质期，不恢复数量或单位。过期由服务端按家庭日期判定；过期当天是否可用依服务端状态，不靠设备日期另算。过期不自动报损；部分报损仍可有剩，变质批次仍不可用于做菜和建议。
- 做菜页读取菜单快照而非已修改的菜谱，优先提示临期可用批次；未填写日期的排最后。用户选择实际批次，提交其 ID、版本和 `usedUp`，不按食材名清空全部批次。未选到的食材提示补记库存。
- 保存菜谱、安排菜单和查看建议均不消耗库存。只有实际做菜确认后显示消耗结果；`usedUp=false` 保留有剩，采购单仍沿用 ROBB-6 菜谱“是否用完”规则，不按库存自动过滤或自动采购。
- 相同写意图重试复用 `requestId`，由 `CloudClient.call` 第四个参数传给请求信封。做菜响应丢失时保留原选择与请求 ID，不误报成功或允许另改一份确认；重试恢复幂等回执。版本冲突刷新批次后要求用户再次确认，不自动写入或换用另一批同名食材。
- AI 手动请求，库存/记录/AI 有独立加载和错误状态。库存变更清除旧建议并忽略迟到结果；失败不阻塞库存操作。服务端区分可匹配与需补购，页面不承诺分量足够。过期、变质及 AI 建议均不能代替食品安全判断。
- 页面回归命令：`node --test tests/miniprogram/fridge-inventory.test.js tests/miniprogram/fridge-cook.test.js`。TypeScript 使用项目 `tsconfig.json`，以 CommonJS 生成随小程序提交的 `.js`。
- 本地链路验证已运行编译后页面、云端适配器及 ROBB-16 真实 handler/repository/suggestion 逻辑，数据库与登录使用内存夹具；覆盖同名多批次、冲突原子性、响应丢失重试、部分/全部报损、AI 未配置失败和采购兼容。AI 成功分支仅验证输出夹具与服务端匹配，不等同于真实 AI 调用。
- 发布验收仍需部署 ROBB-16 的云函数与数据库索引，落实服务端 AI 接入配置，再在微信开发者工具或真机完成完整链路与布局验证；不能用本地夹具或浏览器近似预览代替。


## 8. 安全、隐私与合规

- 使用最小权限：云函数按动作限制角色，数据库规则作为第二道防线；服务账号不下放客户端。
- 所有字符串、数组长度、日期、ID 和上传元数据做 schema 校验；拒绝原型污染字段和超大请求体。
- 图片仅允许 JPG/PNG/WebP，单张不超过 5 MB；服务端检查 MIME、扩展名和实际大小，生成缩略图并使用短期下载 URL。
- OpenID、UnionID、过敏信息、操作日志按敏感级别访问；日志禁止打印 token、邀请码明文和完整个人偏好。
- 提供隐私政策、用户协议、注销和数据删除入口；注销前明确说明家庭历史数据的匿名化保留规则。
- 按微信小程序要求完成备案、类目选择、内容审核和隐私弹窗；菜谱图片和文字需支持举报/删除（首版可仅管理员处理）。
- 记录成员变更、管理员转移、菜谱删除、清单清空等审计事件：操作者、家庭、动作、资源、结果、时间、请求 ID。
- 对登录、加入家庭、投票和上传接口限流；异常登录和短时大量失败请求触发告警。

## 9. 测试方案与验收

### 9.1 测试层级

- 单元测试：日期/周起始计算、食材标准化与合并、投票唯一性、角色判断、分页游标。
- API/云函数测试：未登录、跨家庭 ID、已移除成员、非法参数、重复 `requestId`、版本冲突。
- 页面测试：登录、创建/加入家庭、首道菜、排餐、投票、购物勾选、偏好和反馈的成功/失败/空状态。
- 并发测试：多个成员同时投票、同时编辑同一菜单、同时生成清单；验证唯一约束和乐观锁。
- 兼容性测试：目标微信基础库、主流 iOS/Android 机型、弱网和断网恢复、图片上传失败恢复。
- 性能测试：首页首屏、菜谱搜索 P95、周菜单接口 P95、图片上传成功率；建立基线后设告警阈值。
- 安全测试：越权读取/修改、重放请求、注入字段、超限上传、敏感日志和注销数据清理。

### 9.2 发布验收清单

- [ ] 新用户 3 分钟内创建家庭并添加第一道菜。
- [ ] 家庭成员首页看到当天菜单和正确的投票/购物待办。
- [ ] 同一成员无法重复投票，重复请求不会增加票数。
- [ ] 不同家庭之间无法读取或修改彼此数据，移除成员立即失权。
- [ ] 一周菜单按标准名称和单位正确汇总购物清单。
- [ ] 断网、无权限、空数据、校验错误和接口异常均有明确反馈与重试。
- [ ] 生产环境已启用日志、关键指标告警、备份、灰度和回滚。
- [ ] 隐私政策、用户协议、注销和数据删除流程可用，审计事件可查询。

## 10. 部署、监控与运维

### 10.1 CI/CD

1. Pull Request 运行 TypeScript 类型检查、ESLint、单元测试和构建；禁止有错误合并。
2. 合并到 `develop` 自动部署 `dev`，发布候选分支部署 `test` 并执行 API/页面回归。
3. 生产发布由至少一名管理员审批，先发布云函数和数据库迁移，再以小比例灰度小程序版本。
4. 观察错误率、P95 延迟和关键业务成功率后扩大灰度；异常时停止扩大并回滚函数/小程序版本。

数据库索引和迁移脚本版本化，迁移必须向后兼容旧客户端；破坏性字段删除至少跨两个版本。

### 10.2 监控指标与告警

- 云函数：调用量、错误率、超时率、P50/P95 延迟、冷启动占比。
- 业务：登录成功率、家庭创建成功率、投票重复冲突率、清单生成失败率、图片上传失败率。
- 客户端：启动耗时、首屏渲染、页面崩溃、网络失败、版本分布。
- 告警：错误率 > 2% 持续 5 分钟、P95 超过基线 2 倍、备份失败、存储异常；通知值班群并带 `requestId` 示例。

### 10.3 备份、恢复与反馈

每日数据库备份、每周恢复演练，保留周期按合规和成本确定；恢复目标建议 RPO <= 24 小时、RTO <= 4 小时。发布后通过用户反馈入口和问题单系统记录复现步骤、客户端版本、家庭/用户脱敏 ID、请求 ID，按严重程度分派和复盘。
